# 录音产品基线：观测证据驱动的智能排障

> 状态：**现行产品事实来源**
>
> 来源：2026-07-27 企业微信笔记导出的约 28 分钟逐字稿 `id128_note.txt`。
> 原始转写存在口语和识别误差，因此这里只保留被多次重复、能由上下文交叉确认的事实；
> 不把开头的自动 AI 总结当作决策依据，也不把讨论中的脑暴直接升级为工程承诺。

## 1. 会议真正要解决的问题

服务经理或业务人员通常只带来一段现象、截图、视频或客户 ID，开发需要人工完成：

1. 补齐上下文；
2. 在观测云中找到相关日志；
3. 根据 PS ID / trace id 还原完整调用链；
4. 判断异常点、影响范围和责任位置；
5. 把本次排查方法重新写成 SOP。

项目的目标不是再做一个错误码搜索页，而是把这段重复劳动变成一条可审计、可复用的证据流水线。

## 3. 讨论过但没有成为当前承诺的内容

### 3.1 自动执行 SOP / 自愈

开头用友商“能执行 SOP”做了对比，但后续明确：代码缺陷无法由当前系统自动恢复，当前能兑现的是
定位、证据和建议。由此得到的工程边界是：

- 自动只读取证可以做；
- 通知可以自动；
- 生产写不自动执行；
- 人工批准不能等价于工具回放。

### 3.2 浏览器兼容性和客户网络根因

会议明确承认这类根因可能分析不出来。系统最多可以根据其他客户是否正常，给出“平台侧未见异常”的
排除结论，置信度不能包装成已定位。

### 3.3 五类 FaultClass

原始录音只稳定支持两种能力承诺：

- 代码类：定位代码位置，不承诺解决方案；
- 业务/数据类：可以给人工处置建议。

`CODE_BUG / DATA_FIX / BUSINESS_OPERATION / EXTERNAL_CLIENT / INFRASTRUCTURE` 五分类是后续设计推演，
不是会议原始决策。若要保留，应通过真实样本验证，而不是写成录音既定要求。

## 4. 第一性原理约束

从以上事实推导出六条不可妥协约束：

1. **证据先于推理**：没有服务端实际取回的证据，模型不能声称已定位。
2. **草稿不等于权威**：AI 可以直接从证据生成 `PlaybookDraft`，但只有经过审核和回放的 Playbook 才能用于稳定路由。
3. **错误码不是唯一入口**：场景型和探索型必须成为正式产品路径，同时保留不同可信等级。
4. **模型选路不等于确定性命中**：模型推荐场景 Playbook 时，结果必须保留 assisted 标记和置信上限。
5. **一份事实，两种投影**：业务摘要与开发证据来自同一个 Diagnosis，不能各自编造。
6. **自动化止于只读**：生产写始终在 MateClaw 之外由人执行并登记 outcome。

## 5. MVP 验收基线

首个 MVP 必须用会议指定案例验证：

```text
会话消息发送失败（无 error_code）
  → 根据服务 / 客户 / 时间窗检索日志
  → 提取 PS ID
  → 拉取同一 PS ID 的完整链路
  → 确定性压缩成调用链骨架
  → 生成带证据引用的根因假设和排查步骤
  → 与人工当时的解法逐项比较
  → 形成不可直接生效的 PlaybookDraft / KnowledgeCandidate
```

完成必须同时满足：

- 不返回原始日志包、凭据或危险查询；
- 不调用生产写工具；
- 不把模型文本当作证据；
- 不一致样本逐条解释，不能只靠调整 prompt 把单例“调对”；
- recorded replay 只证明工程链路，真实观测云接入必须另有内网验证证据。
