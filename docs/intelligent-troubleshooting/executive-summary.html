IT 智能排障系统

把一条不完整报障，转成带证据、可交接、可复用的定位结论。系统运行在 Java MateClaw 内，以观测云日志、PS ID 全链路和人工审核的知识闭环形成差异化。

目标 缩短“报障 → 可核验定位结论”的时间 状态 MateClaw-only v4 · 架构评审通过 · P1 可实施

为什么值得做

痛
服务经理只带来现象、客户或截图，开发要反复补问、翻日志、追链路，再重新写排查步骤。

同类故障重复消耗开发时间，定位过程不可审计，处理完也没有稳定成为下次可复用的方法。

机
团队拥有观测云日志，能从样本日志提取 PS ID 并还原同一请求的完整链路。

这使“先取证、再推理、再形成待审核知识”成为可验证的工程路径，而不是泛化聊天机器人。

核心做法（三条）

1
一条证据脊柱，两个闭环。

Incident → 只读 EvidencePlan → EvidenceBundle；同一份证据既支撑在线诊断，也支撑 PlaybookDraft，不复制取证逻辑。

2
三类路径，权威不混淆。

错误码命中保持零 LLM；场景允许模型提议已注册 key，最高 MEDIUM；未知探索受 DiscoveryPolicy 约束，证据不足必须弃权。

3
草稿不是权威，自动化止于只读。

PlaybookDraft 必须经过引用校验、人工参考比较、历史回放和专家审核；生产写始终在系统外由人执行并登记 outcome。

一句实话（关键判断）

当前只能证明 Recorded Replay 的工程链路能跑到 READY_FOR_MODEL，不能声称真实 Guance 已验证，也不能声称 SOP 已自动生成。P1 仍需完成结构化 PlaybookDraft、领域校验、人工参考解法比较与 candidate 幂等；真实数据在 P2 单独验收。

怎么安全地放权

证据先行没有本次服务端证据，就不能声称已定位
路由可见EXPLICIT / RULE_MATCHED / MODEL_PROPOSED 分开展示和统计
知识审核草稿、候选、审核、批准、废弃单向推进，批准创建新版本
只读边界自动取证和通知可以做；改配置、改数据、改代码和恢复动作永远不自动

第一步 · 需要的支持

已做： 录音事实基线、MateClaw-only v4、架构师评审、现有证据预演与 A/B/C Demo。
下一步： 用“会话消息发送失败（无错误码）”完成 PlaybookDraft → Validator → ReferenceSolution → candidate。
需支持： ① 用户选择 A/B/C 信息结构；② 提供会议案例的人工参考解法；③ P2 时提供可访问真实 Guance 的内网环境与历史样本。
一句话总结：用 MateClaw 把报障变成有界只读取证，再把同一份证据变成可核验诊断和待审核知识；模型帮助归纳，但证据、批准和生产写权始终掌握在系统规则与人手里。
