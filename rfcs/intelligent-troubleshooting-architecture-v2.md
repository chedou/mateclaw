# IT 智能排障系统 · 架构 v2（第一性原理重做）

> 取代 `rfcs/intelligent-troubleshooting-design.md`（下称 v1）作为**现行架构**。
> v1 不作废：它逐条核对过 MateClaw 源码，§12 源码索引与 §5 红线论证仍然有效，作为**证据附录**保留。
> 本文只做一件事：**把这套系统从公理重新推一遍**，看 v1 哪些结论是从公理来的（保留），
> 哪些是从当时的偶然条件来的（推翻）。
>
> 触发重做的外部输入：2026-07 会议指出**只做错误码匹配是没有价值的**——研发团队把代码交给 AI
> 也能做到同样的事；我们唯一的结构性优势是**自有观测云全量日志**。
> 会议纪要 → 变更方案见 `docs/intelligent-troubleshooting/meeting-change-plan.md`。

## 0. v1 的建模错误（结论先行）

v1 把**知识的身份**定义成了 `(system, error_code)`：

```java
public String routingKey() {           // SopEntry
    return system + ":" + errorCode;   // errorCode 是必填字段
}
```

这句代码里藏着三个被当成公理、其实只是偶然条件的假设：

1. 每个故障都有错误码 —— **假的**。会议指定的验收案例「会话消息发送失败」就没有错误码。
2. 错误码能唯一确定排查方式 —— **假的**。L0 清洗已经暴露 `101014/101034/101040` 一码多义。
3. 排查知识由人书写 —— **v1 的真正天花板**。人写多少，系统就会多少；人不写，系统就是个查表器。

第 3 条最致命：**v1 没有学习机制**。它把"知识从哪来"这个问题外包给了人，于是系统的价值上限
等于运维团队愿意写多少文档——那正是这套系统本来要解决的问题。

v2 的核心修正：**把"触发方式"从知识的身份里拆出来，并把"从日志归纳知识"变成架构的一等公民。**

## 1. 公理：不可再分的约束

| # | 公理 | 为什么不可再分 |
|---|---|---|
| **A1** | 故障的真相只存在于**证据**里（日志/指标/链路/拓扑），不在人的记忆里，也不在模型的权重里 | 系统外部世界的性质，不由我们选择 |
| **A2** | 模型不产生事实，只做**归纳与表达**；它能生成"看起来完全合理的错误结论"，**且错误是无声的** | LLM 的本质属性 |
| **A3** | 生产变更的风险由组织承担，**不由本系统承担** | 授权边界，不是技术选择 |
| **A4** | 我们相对研发团队唯一的结构性优势是**持有全量观测云日志**；代码、模型、算力人人可得 | 会议 M2 给出的外部事实 |
| **A5** | 人的时间是最稀缺资源；系统价值 = **节省的排查时间 × 结论可信度**。可信度为 0 时，节省再多时间也等于 0 | 价值定义 |
| **A6** | 知识会过期。系统对错误码/字段/阈值的每一条假设，都在被现实持续证伪 | 时间的性质 |

## 2. 从公理推出的定律

**L1 · 证据优先（A1）**
任何结论必须可回溯到**一次具体的证据查询**。没有 `queryId` 引用的判断，不是结论，是猜测。
→ `EvidenceResult` 是一等公民；模型输出里未被服务端取证会话验证过的引用一律作废。

**L2 · 判定必须确定性（A2 + A5）**
从证据到结论那一步必须**可复算、可解释、可回归**。
因为 A2 说模型的错误是无声的，而 A5 说可信度为 0 时系统价值为 0——所以**判定链里不能有模型**。
→ 判据（`Criterion`）和规则（`DiagnosisRule`）是**数据**，不是 prompt；`CriterionEvaluator` 是纯函数。

**L3 · 模型只在两个位置合法（A2 + A4）**
```
① 入口分诊：自然语言/上下文 → 选哪条 SOP。输出被强制约束在枚举内，选不中就落未命中路。
② 知识归纳：全链路日志 → SOP 候选。产物必经人审，永远不直接生效。
```
除此之外模型不进入主链。这两处的共同点是：**模型的输出会被一道确定性闸门接住**
（枚举约束 / 人工审核），所以 A2 的"无声错误"变成了有声的。
判定链里没有这样的闸门，所以模型不能进去。**这条就是 D1′ 的完整推导。**

**L4 · 学习环是架构的一等公民（A4 + A6）**
A4 说我们的优势是日志，A6 说知识会过期。两者合起来：**系统必须能从日志里自己长出知识**，
否则优势兑现不了，且知识会随时间衰减为 0。
→ `SopSynthesisService`（日志 → 调用链骨架 → 候选 SOP）不是"锦上添花的功能"，
它是**系统唯一的自增长机制**，与执行链路同等地位。

**L5 · 输出必须分层（A5）**
同一份诊断，对服务经理、对开发、对审计是**三种不同的正确形态**。
把三者混在一个页面上，等于对三种人都不可用——这正是当前详情页的病。
→ 底层是同一个可复算结构，上层是**投影**。见 §8。

**L6 · 系统的承诺必须随故障类别变化（A3 + A5）**
代码 bug 只能定位（改代码是生产变更，A3 禁止）；客户端问题只能排除；数据/业务问题才能给方案。
承诺超出能力，可信度归零，按 A5 系统价值归零。
→ `faultClass` 决定输出**形状**，不是一个展示标签。

## 3. 三个环：系统的真正骨架

v1 只画了执行链路，于是"知识从哪来"没有归宿。v2 的骨架是**三个不同频率的环**：

```
        ┌──────────────── 执行环（秒级）─────────────────┐
报障 →  分诊 → 取证 → 判定 → 结论 → 人处置 → 结果登记 → 关闭
        └───────────────────┬───────────────────────────┘
                            │ 关闭时沉淀
        ┌───────────────────▼──── 学习环（小时/天级）────┐
   全链路日志 → 确定性压缩 → 模型归纳 → SOP 候选 → 人审 → 入库
        └───────────────────┬───────────────────────────┘
                            │ 新知识进入下一次执行
        ┌───────────────────▼──── 信任环（周/月级）──────┐
     影子回放 → 自动 vs 人工一致率 → 放权档位 S0→S3
        └───────────────────────────────────────────────┘
```

- **执行环**决定单次故障的处理速度 —— v1 已建成。
- **学习环**决定系统的**能力增长速度** —— **v1 完全缺失，v2 的主攻方向**。
- **信任环**决定系统被允许自主到什么程度 —— v1 有设计（D5），未实现。

**第一性判断：系统的价值上限由学习环的产出速度决定，不由执行环的性能决定。**
执行环再快，能处理的故障种类也只等于知识库里有的那些。所以工程排期上，学习环优先。

## 4. 知识的正确分解

v1：`SOP = (system, error_code) → 判据 + 规则 + 动作`
v2：**四个正交维度**，任何一个都不进入另一个的身份

```
SOP = 触发器(Trigger)  ×  判定程序(Program)  ×  动作模板(Actions)  ×  来源(Provenance)
```

| 维度 | 取值 | 说明 |
|---|---|---|
| **触发器** | `code:{system}:{errorCode}`<br>`scenario:{system}:{scenarioKey}`<br>`generic:{system}` | 只回答"什么时候用这条 SOP"。错误码只是**三种触发方式之一**，不再是身份 |
| **判定程序** | `EvidenceRequest[]` + `Criterion[]` + `DiagnosisRule[]` | 纯数据、可复算、可回归。**这才是知识的本体** |
| **动作模板** | `RecommendedAction[]`，受 `faultClass` 约束 | `CODE_BUG` 类不得产出恢复动作（L6） |
| **来源** | `HUMAN_AUTHORED` / `SYNTHESIZED_FROM_LOGS` / `DERIVED_FROM_CLOSURE` | 审核时人需要知道这条是谁写的；合成的要看得更严 |

**由此自然得到的三类 SOP**（会议 M3 的分类不是拍脑袋，是这个分解的推论）：

| 类 | 触发器 | 典型判定程序 | 会议评价 |
|---|---|---|---|
| 错误码类 | `code:` | 码 → 已知原因 → 取证确认 | "傻瓜似的"，低价值但便宜 |
| **场景类** | `scenario:` | 慢接口：观测云查慢接口清单 → 定位代码 → 分析<br>系统挂：主机 → K8S pod → 近 30 分钟慢接口 → 推断网元 | **价值最高**，v1 完全承载不了 |
| 通用兜底类 | `generic:` | 日志 → 全链路 → 模型分析 | 保证任何报障都有路可走 |

**存储影响**：`mate_troubleshooting_sop` 增 `kind` / `scenario_key` / `provenance` 三列；
`route_key` 列复用，值改为 `RouteKey.toStorageKey()`。`(workspace_id, route_key)` 唯一约束保留，
但**必须同时解决 v1 遗留的版本化问题**：deprecated 记录仍占用 routeKey，导致无法为同一路由注册
替代版本。v2 定为「历史多版本 + 唯一 current 版本」：唯一约束改为
`(workspace_id, route_key, current)` 上的部分唯一或以状态列参与，审计轨迹不得靠覆盖行抹掉。

## 5. 分层：每层一个职责，以及**不许做什么**

| 层 | 职责 | **禁止** |
|---|---|---|
| **L0 证据层**（OAL） | `signalKind` 语义 → 平台适配器（观测云 / K8S / 代码检索）。系统里**唯一**与外部耦合的地方 | 禁止出现任何写操作；禁止把平台方言（DQL 串）泄漏到上层 |
| **L1 判定层** | `Criterion` 求值、`DiagnosisRule` 裁决、`Confidence` 定级。**纯函数，无 IO** | 禁止调用模型；禁止访问数据库；禁止依赖 L2 的存储 |
| **L2 知识层** | SOP 的四维分解、生命周期 `candidate→approved→deprecated`、**合成器**（日志→候选） | 禁止合成产物直接生效；禁止状态回退 |
| **L3 编排层** | 爆炸半径前置 → 分诊 → 取证 → 判定 → 落库 → 状态机 | 禁止走 Trigger 引擎（`targetType` 只有 agent\|workflow，workflow 每步调 LLM） |
| **L4 交付层** | 三种受众投影 + 通道（Web / 企微 / 飞书） | 禁止在通道上放"批准生产写"入口——摘要不足以支撑该决定 |
| 横切 | 身份鉴权（复用 RBAC/JWT/PAT/SSO）、脱敏、影子与放权 | 未绑定 MateClaw 身份的 IM 点击一律拒绝（不可追责的身份等于废掉审批） |

**L1 不依赖 L0 也不依赖 L2 的存储**，这条是信任环的地基：判定层是纯函数，才能对历史样本做
影子回放、算一致率。任何"为了方便"在 L1 里塞 IO 的改动，都是在拆信任环。

## 6. 一次报障的完整数据流

```
0. 接入        企微 @ 机器人 / Web 报障 / 工单 webhook（PAT 鉴权，不走 Trigger）
               信息不足 → AWAITING_INPUT，回帖索要客户ID/截图 → 补齐后继续

1. 爆炸半径    blast_radius_probe：同错误在窗口内的客户维度分布      ← 必须前置
               ├ SYSTEM_WIDE / MULTI_CUSTOMER → scenario:system_down
               └ SINGLE_CUSTOMER 且他人正常   → 排除法结论（见下）

2. 分诊        ① 确定性触发器匹配（错误码 / 症状关键词 / service / 指标特征）
               ② 未命中 → 受限分诊模型，输出约束在 scenarioKey 枚举内
               ③ 仍未命中 → generic 兜底 或 只读 Agent 未命中路

3. 取证        EvidenceSourceRouter 按 signalKind 派发；命中路与未命中路共用同一 router
               结果归一为 EvidenceResult{status: NORMAL|ANOMALY|MISSING}

4. 判定        Criterion 三态求值：SATISFIED / EXCLUDED / UNEVALUATED
               DiagnosisRule 按序裁决 → 根因假设 + Confidence
               ★ 全程零模型

5. 输出        按 faultClass 决定形状（§7）；三种受众投影（§8）

6. 处置        人确认 → 转派 / 批准（只推进状态机）→ 外部执行 → record-outcome → 关闭

7. 沉淀        关闭时产出知识候选；学习环另从日志侧合成候选；两路都必经人审
```

**为什么爆炸半径必须前置**（会议 M9，但理由比会议给的更强）：
「是不是我们的问题」在逻辑上**先于**「是什么问题」。单客户 vs 全局决定了整个假设空间——
在错误的假设空间里做再精确的判定也是错的。v1 把它塞进 `IncidentContext.impact` 这个自由文本
字段，等于把一个前置判断降级成了展示信息。

**排除法结论的诚实约束**：单客户路径输出的是**排除**不是**定位**，
`Confidence` 不得高于 `MEDIUM`，且必须显式区分 `EXCLUDED`（判据求值为假，真的排除了）
与 `UNEVALUATED`（证据缺失，根本没验过）。这两者在语义上是相反的，混显是诊断安全事故。
浏览器兼容性问题**明确不做**（会议自己承认分析不出来），只做到"系统侧未见异常"。

## 7. 能力边界矩阵（L6 的落地）

| `faultClass` | 系统承诺 | 输出形状 | 禁止 |
|---|---|---|---|
| `CODE_BUG` | **只定位** | 代码位置（类/方法）+ 片段 + 证据链 | 不给解决方案、不给恢复动作 |
| `DATA_FIX` | 可给方案 | 建议动作（人在平台外执行，回来登记） | 平台不执行 |
| `BUSINESS_OPERATION` | 可给方案 | 操作指引 | —— |
| `EXTERNAL_CLIENT` | **只排除** | "系统侧未见异常"+ 支撑证据，`Confidence ≤ MEDIUM` | 不声称定位到客户端根因 |
| `INFRASTRUCTURE` | 定位到网元/节点 | 受影响组件 + 影响面 | 不执行恢复 |

会议原话为这张表背书：「你现在只能做到一个事情，是定位到问题，解决方案那种给不了」。
**这不是我们能力不足的遮羞布，是产品承诺的边界，要主动讲。**

## 8. 三种受众投影（L5 的落地）

同一个 `Diagnosis` 聚合，三个投影，**默认只给第一个**：

| 投影 | 受众 | 内容 | 默认 |
|---|---|---|---|
| `BusinessSummary` | 服务经理 / 二线 / 业务 | ① 问题是什么 ② 影响谁（功能影响 + 影响人数）③ 怎么办 | **展开** |
| `DiagnosisDerivation` | 开发 | 判定链：证据 → 判据（带代入算式、三态）→ 规则（带反事实）→ 结论 | **折叠**，一键展开 |
| `AuditTrail` | 审计 / 排障系统自身 | timeline、warnings、routeMode、fixtureMode、契约版本、审批与登记记录 | 需要时才进 |

**当前实现违反了这条**：详情页第一屏就是 `routeMode` / `fixtureMode` /
`writeExecutionEnabled=false` 三个 pill + warnings 告警条 + 裸枚举 `approvalStatus`——
把审计投影当成了主视图。会议对此的评价是「太花哨了」「PSD 他肯定看不懂」。
详情页重做见 `docs/intelligent-troubleshooting/detail-page-design.md`。

## 9. v2 相对 v1 的变更清单

| # | v1 | v2 | 依据 |
|---|---|---|---|
| 1 | SOP 身份 = `(system, errorCode)` | SOP = 触发器 × 判定程序 × 动作模板 × 来源 | §0、§4 |
| 2 | 无学习环，SOP 靠人写 | 学习环是一等公民，`SopSynthesisService` | L4 |
| 3 | 「零 LLM」= 整条命中路径 | 「零 LLM」= **判定链**；模型在分诊、归纳两处合法 | L3（D1′） |
| 4 | `impact` 是自由文本 | 爆炸半径是**分诊前置**，`IncidentImpact` + `BlastRadius` | §6 |
| 5 | 结论形状统一 | 形状随 `faultClass` 变化 | L6 |
| 6 | 一个详情页塞三种受众 | 三投影，默认只给业务视图 | L5 |
| 7 | 三个 signalKind | 六个（+`log_search`/`log_trace_bundle`/`interface_latency_rank`/`blast_radius_probe`/`k8s_workload_health`/`code_lookup`） | A4 |
| 8 | deprecated 行占用 routeKey，无法换版本 | 历史多版本 + 唯一 current | A6 |

**v1 中被公理支持、因此原样保留的结论**（不要在重构里顺手改掉）：

- 命中路不能是 native Workflow（`AgentStepExecutor` 每个干活步都调 LLM）——L2 的直接推论；
- 接入不走 Trigger（`targetType` 只有 `agent`|`workflow`）——同上；
- ToolGuard「批准」= **回放执行**，与"批准但不执行"语义相反 → 生产写永不挂 ToolGuard——A3；
- 人工确认只推进状态机、执行 0 个工具；`/execute` 恒 409——A3；
- 未命中路 Agent 锁死只读、硬工具白名单、服务端取证会话——A2 + A3；
- 未绑定身份的 IM 点击拒绝——横切纪律。

## 10. 不变量（从公理推出，非偏好）

| 不变量 | 出处 |
|---|---|
| 生产写工具一个都不注册 | A3 |
| 人工确认只推进领域状态机，执行 0 个工具 | A3 |
| 写操作永远外部人工 + `record-outcome` 登记 | A3 |
| 判定链里没有模型 | A2 + L2 |
| 未命中路 Agent 只读，且只有一个工具函数 | A2 + A3 |
| 合成的 SOP 只能落 `candidate` | A2 + L3 |
| 结论必须带可验证的证据引用 | A1 + L1 |
| 宁可承认做不到，也不假装做到了 | A5（可信度为 0 → 价值为 0） |

最后一条不是情怀。按 A5，系统价值 = 节省时间 × 可信度；**一次"看起来合理的错误根因"造成的
可信度损失，会抹掉之前所有正确结论积累的价值**。所以 `fixtureMode` 恒 true、未命中返回 409、
推导 `faithful=false`、身份未绑定即拒绝——这些"示弱"设计是价值最大化的选择，不是保守。

## 11. 迁移路径（不推翻已交付的部分）

已交付的 L0/L1/L3/L4 骨架**全部保留**，v2 是**加维**不是重写：

1. **P6 学习环 MVP**（最高优先）：L0 加 `log_search` / `log_trace_bundle`；
   L2 加 `SopSynthesisService`；跑通会议指定的「会话消息发送失败」一个案例。
   *前置：内网验证 PS ID 是否全链路贯通——不通则整条流水线要换方案。*
2. **P7 触发器泛化**：`SopKind` + `RouteKey` + 两个场景 playbook；分诊两段式。
3. **P8 契约 v1.4**：`IncidentImpact` + `BlastRadius` + `faultClass`，一次迁移 V174。
4. **P9 交付层**：详情页三投影重做（见 §8）；企微接入 + 服务经理闭环。
5. **不排期**：自动改代码注错误码、执行 SOP 自愈。

## 12. 明确不做

| 不做 | 理由 |
|---|---|
| **执行 SOP 自愈**（调本机命令恢复业务） | A3。且会议自身已论证 bug 类"恢复不了" |

| 新的展示层原型 | 会议原话「太花哨了」；交付层收敛到**一个**详情页 |
